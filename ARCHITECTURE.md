# Архитектура Пихты v3

## Границы модулей

- `booking_flow.py`: порядок шагов, обязательные данные, переходы к недостающему шагу, миграция черновика, границы счётчиков, адреса кнопок с версией. Не обращается к Telegram и БД.
- `booking_domain.py`: расчёт, ограничения дат/отмены, карточка записи. Нет сетевых вызовов.
- `booking_store.py`: транзакции, снимки, права доступа, лимиты, занятость, черновики, финальная проверка цены/согласия, аудит, очередь уведомлений.
- `booking_ui.py`: тексты, изображения и клавиатуры Telegram. Не меняет исходные снимки SQL-запросами.
- `admin_web.py`: панель и её формы; использует те же операции хранилища. Авторизация, CSRF, проверка роли обязательны.
- `bot.py`: запуск, один polling-процесс, очередь доставки и резервные копии.
- `bot_features.py`: явное подключение дополнительных модулей, команд и пунктов меню. В первом выпуске список пуст.

Сохраняем проверенное транзакционное хранилище; новое ядро разговора не требует уничтожать данные или заново создавать таблицы.

## Контракт нового модуля

1. Создать собственный Router и фабрику Feature. Ключ уникален (`[a-z][a-z0-9_]{0,15}`). Кнопки начинаются с `feature:<key>:`; предел Telegram — 64 байта. Реестр не допускает конфликта ключей, команд или повторного Router.
2. Добавить фабрику только в `configured_features`. Реестр сам включает её пункт в главное меню, команды и router до обработчиков по умолчанию. Фильтр callback_query ограничивается префиксом модуля. Обработчики текстовых сообщений обязаны иметь собственные фильтры состояния/команды; нельзя перехватывать все сообщения.
3. Данные модуля хранятся отдельно, миграции версионируются и тестируются на существующей БД. Ссылка на бронь хранится по id. `BookingStore.get` проверяет владельца. Цена, дата, контакты и число гостей исходной отправленной брони не переписываются.
4. Общие операции отмены, учёта денег, уведомлений вызываются через проверяемые методы хранилища. Не создавать второй календарь занятости и не отправлять уведомления до фиксации операции в БД. Привязанные операции должны явно описать поведение при отмене/завершении родительской записи.
5. Повторное нажатие и повтор доставки не должны повторять финансовую/учётную операцию. Нужны ключ идемпотентности, повторная проверка прав и текущего статуса в транзакции.
6. Перед подключением: тесты модуля + вся регрессия бронирования. Отключение модуля убирает его пункт и Router; данные и бухгалтерская история сохраняются. Не считать произвольное будущее расширение безопасным без проверки совместимости.

## Устойчивость

Черновики и версии живут в PostgreSQL. Кнопка содержит token и revision; несвежая кнопка не меняет данные. При отправке revision повторно проверяется под общей транзакционной блокировкой; повтор уже выполненной отправки возвращает тот же id. Вместимость, срок записи, цена, согласие, лимит записей и свободное время проверяются на сервере. Исходные снимки защищены триггером.

Навигация в главное меню сохраняет черновик; явный сброс/отмена требуют подтверждения. Изменение профиля временно сохраняет состояние черновика отдельно и не меняет его контакты. При уходе в меню несохранённое изменение профиля отменяется.

## Последующие этапы

Допуслуги, точный склад, нестандартные ручные брони и другие возможности — самостоятельные будущие модули с отдельными требованиями. В v3 нет их пунктов, скрытого каталога или незавершённых переходов в пути гостя.
