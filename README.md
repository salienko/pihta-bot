# Пихта — бот бронирования и веб-панель

Python 3.11, aiogram, PostgreSQL. Без Mini App и без предоплаты. Правила владельца от 21.10.2026 заменяют предыдущий сценарий приёма заявок.

## Текущий выпуск — бронирование v3 (22.10.2026)

Имя → телефон → гости → календарь → время → проверка и согласие → отправка администратору.
Главное меню — inline-кнопки под сообщением. Постоянной нижней клавиатуры нет.
Штатная кнопка передачи своего номера появляется только по запросу гостя и затем скрывается. Можно ввести другой номер.

Черновик сохраняется между посещениями. Гость может продолжить, изменить отдельное поле, начать заново или отменить оформление с подтверждением. Счётчики обновляют подпись существующего сообщения; старые кнопки защищены версией черновика. Итог проверяет актуальную цену и доступность заново. Отправка идемпотентна.

Мои бронирования: отдельная кнопка каждой записи, полная карточка, действующие/история, данные для будущих заказов. Ожидающую заявку можно отменить в любое время, подтверждённую — за 24 часа и раньше. Отправленная бронь неизменяема.

Панель сотрудника: новые заявки отдельно, календарь, подтверждение/отказ/отмена, оплата/возврат как фиксация факта, фактическое посещение, неявка, блокировки, ручные праздничные тарифы, сообщения гостю и журнал. Нестандартное время — через администратора вне самостоятельной записи.

Допуслуги не входят в эту версию. Это не переключатель скрытого интерфейса: новый путь не содержит состояний заказа товаров. Код прежнего каталога и старые снимки сохраняются для совместимости истории, не подключены к меню. Будущий модуль подключается отдельно по [ARCHITECTURE.md](ARCHITECTURE.md).

## Совместимость

Схема данных бронирований сохраняется. Старые незавершённые черновики переводятся на первый шаг новой версии с сохранёнными контактами и новым согласием. Отправленные брони, суммы и история не переписываются. Старые кнопки не меняют новый черновик.

## Настройка
- `BOT_TOKEN`, `DATABASE_URL` — существующие секреты хостинга; не помещать в Git.
- `ADMIN_TELEGRAM_IDS` — числовые Telegram ID сотрудников через запятую.
- `OWNER_TELEGRAM_ID` — владелец, дополнительно включается в список доступа.
- `WEB_BASE_URL` — HTTPS origin панели, без пути. Без него веб-сервер не запускается.
- `PORT` — порт HTTP внутри контейнера, по умолчанию 8080.
- `BACKUP_DIR` — постоянное хранилище; по умолчанию `/app/data/backups`.

Запуск: `python bot.py`. Один экземпляр polling на токен. Сотрудник открывает бота и отправляет `/admin`: ссылка одноразовая, действует 5 минут. Сессия панели — 8 часов. Секреты сессии хранятся в базе только в виде хеша; cookie Secure, HttpOnly, SameSite=Strict. Формы защищены CSRF и проверкой Origin. Контакты доступны только соответствующему клиенту и настроенным сотрудникам.

## Хранение и безопасность операций
Новая схема `pihta_booking_v2`. Прежняя `pihta_intake_v1` не изменяется; её заявки доступны в архиве панели и истории соответствующего клиента. Перед переключением проверить будущие прежние заявки и при необходимости закрыть их время вручную в новом календаре. Создание схемы идемпотентно, существующие снимки не переписываются. Все операции занятости сериализуются advisory lock, повторная отправка не дублирует бронь. Триггер БД защищает исходный состав. Доставка уведомлений отделена от сохранения заказа; возможен повтор уведомления при аварии после принятия Telegram, но заказ не дублируется.

## Проверка
`python -m unittest discover -v`. Для обязательной проверки базы задайте `TEST_DATABASE_URL` на отдельную тестовую PostgreSQL. Тесты создают уникальные схемы `test_booking_*` и удаляют только их. Отсутствующая тестовая база означает пропущенные проверки, а не успешную проверку БД. Рабочую строку подключения в тестах не использовать.

## Резервное копирование
`python backup.py`. Согласованный JSON-снимок новой схемы, без токенов входа и сессий. Автоматически выполняется каждые 6 часов в постоянное хранилище. Копия содержит контакты — не публиковать. Сохранять внешнюю копию штатными резервными копиями хостинга. Перед обновлением сохранить также схему старой версии. Откат: остановить новый процесс, вернуть ветку `order-intake-2026-10-16` и прежние настройки запуска, запустить. Новые брони останутся в `pihta_booking_v2`; старый бот их не обрабатывает. До возврата к самостоятельной записи сверить обе схемы вручную, чтобы исключить двойную запись.
